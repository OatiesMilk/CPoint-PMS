## 1. What changed

Dylan asked for two things: in **Add rolls** the supplier's tag becomes a dropdown of tag codes (the supplier's own tag
chosen first) followed by the digits, so a code reads `LR-BLC-001`; and the Floor Manager manages the tag list on Inventory.
Dylan chose that the tag **replaces** the supplier's short code in the roll code (Q1, option 1); the other two plan questions
kept their recommended answers (blank digits take the next free number; old Tag numbers stay on old rolls).

- **Floor Manager, Inventory:** a new **Roll tags** button (tag icon, secondary) after **Storage locations**, opening
  `/inventory/tags`: a table of **Tag**, **Supplier**, **Default**, **Rolls using it**, **Status** with **Edit**,
  **Deactivate / Reactivate** and **Remove**, and an **Add tag** dialog (Code, Supplier optional, "Default for this
  supplier").
- **Floor Manager, Add rolls:** each roll row is now **Area**, **Tag** and **Digits (optional)**, with a line under the row
  that shows the code it will get ("Code: LR-BLC-004 (next free)"). The supplier's default tag is chosen first (its tags
  first in the box, then "Other tags"); a new row starts on the tag of the row above. Digits are 1 to 6 numbers; left empty
  the roll takes one more than the highest number the tag has. A code that is already a roll, or repeats in the same save, is
  refused on its row with the next free one, and nothing is saved. The free-text "Supplier's tag" box is gone from Add rolls.
- **Rules:** a tag's code can't change once a roll was made from it; only a never-used tag can be removed (otherwise
  deactivate it); a supplier has one default; a deactivated tag can't be a default and leaves Add rolls; a tag belongs to one
  supplier or to none.
- **Suppliers:** every supplier gets its short code as its first tag, as its default: the migration does it for the existing
  ones (so today's codes and today's default stay as they are, and existing rolls are linked to it), and Settings → Suppliers,
  bootstrap and the demo seed do it for new ones. The demo adds one extra tag, `BLC`, for Bulacan Supplier A (not its default).
- **Unchanged on purpose:** old rolls keep their codes and their free-text **Tag number** (still shown, searched by Find roll,
  printed on labels and claim sheets, corrected in Edit details). Quality Inspector, System Admin and constructors don't get
  Roll tags (403 on the API, Forbidden page).

## 3. How to run the app locally

Prerequisites: Docker Desktop running (database only), `npm install` done, `.env` filled in (`AUTH_SECRET`,
`BOOTSTRAP_ADMIN_PASSWORD`, `DEMO_USER_PASSWORD`, `SEED_DEMO_USERS=true`).

```bash
npm run db:up
npm run db:deploy       # applies the new migration; on a database that already has rolls (T1) first
npm run db:generate     # the Prisma client changed; restart any dev server started before this
npm run dev             # note the port
```

Then, for the clean scenarios, `npm run demo:reset '--' --yes` (PowerShell needs the quoted `'--'`).

Health check: `http://localhost:<port>/api/health` returns OK.

Existing automated tests that cover this area (run these too, with `E2E_BASE_URL` set to the dev server):

```bash
npx playwright test tests/e2e/inventory.spec.ts      # new block "Roll tags (Phase 42, D-139)"; the Add rolls test changed
npx playwright test tests/e2e/admin.spec.ts tests/e2e/rolls.spec.ts tests/e2e/supplier-quality.spec.ts tests/e2e/corrections.spec.ts tests/e2e/capture.spec.ts tests/e2e/auth.spec.ts
```

The e2e helpers add rolls straight in the database (`addInventoryRoll`), so they don't touch the tag rules; the codes they
make still read `LR-<supplier code>-NNN`.

SQL for T1 (psql against the dev database):

```sql
-- every supplier has exactly one default tag, and it carries the supplier's code
SELECT s.code, count(t.id) FILTER (WHERE t."isDefault") AS defaults, count(t.id) AS tags
FROM suppliers s LEFT JOIN roll_tags t ON t."supplierId" = s.id GROUP BY s.id, s.code ORDER BY s.code;
SELECT count(*) FROM roll_tags t JOIN suppliers s ON s.id = t."supplierId" WHERE t."isDefault" AND t.code <> s.code;  -- 0
-- rolls linked to their tag, and the ones that aren't
SELECT count(*) AS linked FROM batches WHERE "tagId" IS NOT NULL;
SELECT code FROM batches WHERE code LIKE 'LR-%' AND "tagId" IS NULL ORDER BY code LIMIT 20;  -- empty unless a supplier's code was edited
SELECT count(*) FROM batches b JOIN roll_tags t ON t.id = b."tagId" WHERE b.code NOT LIKE 'LR-' || t.code || '-%';  -- 0
```

## 6. Out of scope / known issues

- **No migration run yet** where it was written (no database there). T1 is the first real run; report any SQL error verbatim.
- The partial unique index "one default per supplier" from the plan isn't in the migration: Prisma can't express it, so a
  raw index would show as drift on the next `prisma migrate dev`. The rule is kept by the service (setting a default clears
  the supplier's other one, in one transaction), and unit-tested. Two people ticking Default at the same instant could both
  win; report it only if you can reproduce it.
- `roll_code_sequences` stays in the database, unused (dropped in a later clean-up). `demo:reset` still empties it.
- The Add rolls "next free" line is worked out when the page loads. If someone else adds rolls meanwhile, the server still
  uses the real next number, so the saved code can differ from the line; the toast shows the saved codes.
- `docs/USER_MANUAL.pdf` and the manual's screenshots 14 (item with rolls) and the new Roll tags page haven't been retaken;
  Claude does that after the pass. Not part of this run.
- `docs/DEMO_SCRIPT.md` is Dylan's file and isn't changed: its Add rolls step should now say "choose the tag, type the digits".

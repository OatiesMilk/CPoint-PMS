## 1. What changed

- **Quality Inspector, Finish batch and Correct:** when pairs failed, a **What was wrong** section
  appears: one line per defect (a final defect type, the pairs, **Fixable** or **Not fixable**, and for
  a fixable one the stage it **Goes back to**). The lines must add up to the failed pairs; **Other**
  needs a description. After 5 findings of a type in the last 4 weeks a hint ("Usually fixable at
  Sole-ing, 14 of 17") offers **Use this**; it is never filled in.
- **Repairs:** each Fixable line makes a repair job at its stage with a code (`RP-261120-2-1`). The
  stage's constructor (on Capture → My stage) or the Floor Manager marks it **Back for inspection**; it
  then waits in **Batches → Queue** under "Repairs back for inspection" (no due time, not in the tab
  title's due count). The QI chooses **Inspect repair**: Passed, Scrapped and Send some back again
  (stage per line) must add up to the repair's pairs; there is no limit on sending back. Passed
  repaired pairs count toward the quota on the day they pass.
- **Floor Manager:** **Batches → Work in progress** (a third tab; the QI sees it read-only): a card per
  stage with the pairs now, repairs there, **Update count**, and "Assigned today: …" below the figures.
  A repair at a stage can be marked Back, moved to another stage or called **Not fixable after all**
  (reason needed) until it is Back. **Plan days → a planned day → Who works where**: constructors per
  stage, one stage each, suggested from the last working day ("Same as Thu 19 Nov. Save to confirm."),
  editable for today and later planned days, past days read-only. A small Work in progress card on the
  Overview.
- **Capture constructors are at Preparation (Addendum 1, A-95, A-96):** a Shoe Constructor with Capture
  access is at Preparation every working day, read from the flag (nothing stored). In **Who works where**
  they are under Preparation, ticked and locked ("Has Capture access") and aren't offered under the other
  stages; the server refuses them anywhere else ("Sam is a shoe constructor with Capture access, so Sam
  works at Preparation. Choose Preparation, or ask the Admin to remove Capture access first."). Constructors
  without Capture access can go to any stage. The board's "Assigned today" and **My stage** include them
  at Preparation.
- **Shoe Constructor:** **Capture → My stage** at the top: the stage they are assigned to today,
  "pairs here now", **Save count**, "Last counted 14:05 for all of Sole-ing", a reminder when a batch just
  ended, and the stage's repairs with **Back for inspection**. A constructor assigned a stage but
  without camera access gets My stage instead of "Ask the System Admin for camera access."
- **System Admin:** **Settings → Final defect types** (Lifted sole, Glue marks, Loose stitching,
  Scuffs, Other; examples until CPoint gives its list). **Other** can't be switched off.
- **Reports → Operations:** four new sections (Final defects, Where defects come from, Repairs, Work in
  progress); failed pairs from before this phase show as "Reason not recorded". The per-day table's
  **Passed** includes repaired pairs ("incl. N repaired"); `production.csv` and the Operations
  figures follow.
- **Rename:** "Upper making" is now **Construction** (README, CLAUDE.md, user manual, master spec).
- **Demo seed:** failed batches get findings by a fixed rotation (enough Lifted sole and Glue marks for
  the hint, some Scuffs not fixable, one Loose stitching), repairs in every state, stage assignments
  (rotating by day) and twice-daily counts. `demo:reset` clears the new tables; the final defect types are
  kept. CI's `docker` job checks the new data.

## 3. How to run the app locally

Prerequisites: Docker Desktop running (database only), Node.js installed, `npm install` done, `.env` filled in
(`AUTH_SECRET`, `BOOTSTRAP_ADMIN_PASSWORD`, `DEMO_USER_PASSWORD`, `SEED_DEMO_USERS=true`,
`DEMO_LOGIN_TOOLS=true`).

```powershell
docker compose stop app      # the Docker app holds port 3000; stop it first
npm run db:up
npm run db:deploy            # applies 20261120120000_final_defects_and_repairs if it is pending
npm run dev                  # http://localhost:3000
```

Health check: `http://localhost:3000/api/health` returns OK. After `npm run db:generate`, restart `npm run dev`
(a dev server started earlier keeps the old database client in memory).

Extra steps for this change:

- **Run M2 on the current database, before any reset:** it has batches from before this phase, so their
  failed pairs must read "Reason not recorded" in Reports → Operations.
- Then back up and reset: `npm run demo:reset '--' --yes` (PowerShell form). It takes 2 to 3 minutes and seeds the Phase 34
  data.

Existing automated tests that cover this area (run these too):

```powershell
$env:E2E_BASE_URL="http://localhost:3000"
npx playwright test tests/e2e/final-defects.spec.ts tests/e2e/stage-wip.spec.ts --workers=2
npx playwright test --workers=2
```

## 6. Out of scope / known issues

- Reports by period, sort, filter, print and corrections to past days, and correcting a repair's inspection: Phase 35 (A-94).
- The five final defect types are placeholders until CPoint gives its list; the rule for repairs that keep failing (no limit) is an assumption (A-88).
- "Where defects come from" uses the stage the QI chose; a later move by the Floor Manager changes the repair's stage, not the finding.
- A stage count from an earlier day shows "Not counted today" (A-91).
- Repairs appear in the Queue as their own section, under the batches, not mixed into the batch list.
- Phone layouts: only Capture's My stage is new; the board, Plan dialog and reports stay desktop pages.
- Leather defects and the camera checkpoint are unchanged.

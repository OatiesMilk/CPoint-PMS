### F2 — C12: corrections e2e submits a stale timestamp read in the laptop's time zone

- **Severity:** High (required e2e does not pass; subsequent serial cases do not run)
- **Role / page:** Floor Manager API; `tests/e2e/corrections.spec.ts:252`.
- **Steps to reproduce:** Run the unmodified corrections spec on this laptop in Asia/Shanghai against the fresh dev server. The second test reads `production_check_ins.updatedAt` through `pg`, converts it with `toISOString()`, and submits it as `expectedUpdatedAt`.
- **Expected:** PATCH changing failed pairs returns 409 with “already back for inspection”; changing only finished pairs then succeeds.
- **Actual:** First PATCH returns 409 `STALE`, “This batch was changed by someone else. Refresh to see it.” The lock-message assertion fails and the two following tests do not run.
- **Evidence:** `corrections.log`, `corrections-results.json`, `e2e-corrections/.../error-context.md`, and `fixture-timezone-evidence` in `scenario-evidence.json`. A sampled stored value is `2026-11-21T11:29:15.398Z`, while the SQL client's parsed Date serializes as `2026-11-21T03:29:15.398Z` (8 hours earlier). Manual API checks using the actual API version return the correct batch and repair lock sentences. The initial SQL-derived manual attempts also returned STALE; both initial and corrected requests are retained. The full suite reproduced line 252's failure. The supplemental repair case separately reproduced the same mechanism at lines 422/432: expected “so this inspection can't change”, received “RP-261025-1-1 was changed by someone else. Refresh to see it.” See `corrections-remaining.log` and its JSON/error context.
- **Suggested fix:** Claude should inspect how the new spec reads UTC `timestamp` values through `pg` on a non-UTC host, including its second test and final repair-lock request. Use a consistent UTC representation/current API version while preserving the stale guard and assertions. No time-zone override or test edit was applied in this QA run.
